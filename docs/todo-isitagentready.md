Source requested for this analysis: `https://isitagentready.com/throwaway.sslboard.com` using `Accept: text/markdown`.

> Environment note: direct `curl` from this workspace to `isitagentready.com` and `throwaway.sslboard.com` failed with `CONNECT tunnel failed, response 403`, so this document is based on the scanner categories exposed by the page, the current project implementation, and the existing `/llms.txt` context. Re-run the scanner after each implementation phase and update this file with exact pass/fail rows from the live report.

## Current project context

Throwaway is a public, unauthenticated Cloudflare Worker JSON API and web UI for disposable/invalid email detection. It currently exposes:

- `GET /` static UI from `public/`.
- `GET /check?email=...` and `GET /check?domain=...`.
- `POST /check` for batch email/domain checks.
- `GET /stats`.
- `GET /health`.
- `GET /llms.txt`.
- `GET /robots.txt` generated by the Worker.
- `GET /sitemap.xml` generated by the Worker.
- `GET /llms-full.txt`, `/auth.md`, `/openapi.json`, `/api-catalog.json`, `/.well-known/mcp-server.json`, `/.well-known/agent-skills.json`, `/.well-known/agent-card.json`, and `/mcp` after this implementation pass.

The service has no account system, API key, payment flow, write operations, user-specific state, or protected resources. That matters because several `isitagentready.com` checks are aimed at authenticated applications or commerce sites and should either be intentionally marked "not applicable" or implemented only if the product direction changes.

## Implementation status

This document started as the prioritization analysis. The first implementation pass now adds the recommended no-auth, no-commerce agent-readiness surface: richer robots/sitemap discovery, Link headers, markdown negotiation, `auth.md`, OpenAPI, API catalog, MCP discovery and a lightweight MCP-compatible JSON-RPC route, agent skills, an agent card, and a DNS discovery runbook. OAuth and commerce are intentionally out of scope because Throwaway has no accounts, protected resources, payments, carts, orders, or write operations.

Hono was evaluated as a possible routing improvement, but it was not added because this environment could not fetch new npm packages. The code is still split into route/service modules so Hono can be introduced later with a small router adapter if desired.

## Executive summary

The fastest meaningful path to agent-readiness is:

1. Publish stronger discovery artifacts: static `robots.txt`, complete `sitemap.xml`, `llms.txt` and `llms-full.txt`, OpenAPI, API catalog, and well-known metadata.
2. Add Link headers from the homepage and API responses that point agents to those artifacts.
3. Add markdown content negotiation for `/`, `/check` documentation, `/stats` documentation, and errors where useful.
4. Add explicit bot policy signals: AI bot rules in `robots.txt`, content-signal metadata, and a clear `auth.md` explaining that the public API is unauthenticated.
5. Add a small MCP server facade for the read-only `check_email`, `check_domain`, and `get_stats` tools.
6. Keep OAuth and commerce out of scope: publish `auth.md` to state there is no auth, and do not implement x402/MPP/UCP/ACP unless the product later adds paid or transactional features.

- Add explicit AI-agent crawler sections for bots the project wants to allow, for example `GPTBot`, `ChatGPT-User`, `ClaudeBot`, `Claude-User`, `PerplexityBot`, `Google-Extended`, `Applebot-Extended`, and `CCBot`.
- Add comments documenting the policy: agents may fetch docs and call the public API; there is no login or paid content; abusive traffic may be rate-limited later.
- Add `Sitemap: https://throwaway.sslboard.com/sitemap.xml`.
- Add `LLMS: https://throwaway.sslboard.com/llms.txt` as a non-standard but useful discoverability hint.
- Consider adding `Host: throwaway.sslboard.com` for crawlers that use it.
- Decide whether to keep dynamically generated `ROBOTS_TXT` in `src/index.ts` or move to `public/robots.txt`. Prefer one source of truth.

### 3. Discoverability: Link headers

Current status:

- JSON API responses include CORS/security headers only.
- Static assets use `public/_headers`, but there are no `Link` headers advertising discovery resources.

Required changes:

Add `Link` headers on `GET /`, `GET /check`, `POST /check`, `GET /stats`, and documentation endpoints, such as:

```http
Link: <https://throwaway.sslboard.com/llms.txt>; rel="llms"
Link: <https://throwaway.sslboard.com/openapi.json>; rel="service-desc"; type="application/openapi+json"
Link: <https://throwaway.sslboard.com/api-catalog.json>; rel="service-meta"; type="application/json"
Link: <https://throwaway.sslboard.com/.well-known/mcp-server.json>; rel="mcp-server"; type="application/json"
Link: <https://throwaway.sslboard.com/sitemap.xml>; rel="sitemap"; type="application/xml"
```

Implementation notes:

- Cloudflare Workers can send multiple Link values as one comma-separated header.
- Create a shared `DISCOVERY_HEADERS` constant and merge it into `jsonResponse`, `/llms.txt`, `/robots.txt`, `/sitemap.xml`, and static fallback responses where feasible.
- For static assets, mirror important headers in `public/_headers` for `/`.

Files likely touched:

- `src/index.ts`.
- `public/_headers`.
- Tests asserting the Link header exists.

Priority: **P0 easy win**.

3. **Expose only the server card first**, then implement full MCP in a second phase.
   - Pros: quick scanner progress.
   - Cons: agents still cannot call via MCP.

## Risks and decisions needed before implementation

1. **Exact standards paths and formats:** Several scanner checks refer to emerging standards. Confirm current syntax for DNS-AID, Content Signals, MCP server card, Agent Skills, WebMCP, and A2A before implementing.
2. **No-auth vs OAuth:** Because the API is public, OAuth discovery should not be faked. Prefer `auth.md` and OpenAPI `security: []`.
3. **MCP scope:** Decide whether to ship metadata only first or a complete MCP endpoint.
4. **Crawler policy:** Decide whether all AI crawlers are welcome or only interactive/user-directed agents.
5. **Rate limits:** The docs currently say no rate limits. If agent-readiness increases automated usage, add formal rate limits and document them.
6. **Source of truth:** Avoid duplicating API schemas by generating docs from shared constants or adding tests that keep README, `llms.txt`, OpenAPI, and homepage examples in sync.
